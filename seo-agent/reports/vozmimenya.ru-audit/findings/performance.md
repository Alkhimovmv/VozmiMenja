## Находки

### 1. [HIGH] Сильный CLS на посадочных arenda-* (0.49–0.61) и заметный в блоге (0.10–0.14)
- Доказательство: PerformanceObserver layout-shift. На /arenda-pylesosov-moskva единичный сдвиг 0.611 на ~3.4 с (mobile): блок `SECTION.py-12 "Подобрать пылесос под задачу"` (503px высотой) пропадает/перерисовывается. В блоге: абзац-врезка сдвигается с y=489 на y=742 (0.104). Корневая причина: `client/src/main.tsx` использует `createRoot(...).render`, а не `hydrateRoot`, т.е. пререндеренный HTML выбрасывается и перестраивается React-ом (плюс lazy-чанки страниц и данные из API приходят позже).
- Рекомендация: перейти на `hydrateRoot` для пререндеренных страниц (или хотя бы резервировать высоту блоков, не показывать скелетон/другую вёрстку, отличающуюся от пререндера); убедиться, что DOM первой отрисовки React совпадает с пререндером; для блоков, зависящих от API, задать min-height.
- Проверка: Playwright с observer layout-shift на 3 страницах arenda-*/blog (цель ≤0.1, лучше 0); Lighthouse CLS; позже CrUX/Метрика по 75-му перцентилю. Затронуты, вероятно, все arenda-* и статьи со вставками (проверен лишь 1 экземпляр каждого типа).

### 2. [HIGH] Пререндер отбрасывается (createRoot вместо hydrateRoot): LCP-картинка карточки и блога появляется только после JS+API
- Доказательство: desktop LCP на карточке 2.26 с и в блоге 2.21 с — это IMG, а FCP 0.66/0.55 с. В пререндер-HTML карточки нет `<img>` (curl), картинка (`/uploads/ab3e...jpg`, 1600x1600, 131 КБ) запрашивается на ~1.55 с после запроса `/api/equipment/<slug>` (882 мс). На mobile LCP попадает в текст (P) 1.54 с, но на реальных 4G/слабых устройствах картина будет та же — элемент LCP зависит от API.
- Рекомендация: пререндерить главное изображение (`<img>` с width/height, fetchpriority=high, srcset на -w400/-w800 webp) в статический HTML и `<link rel="preload" as="image" imagesrcset=...>`; вместе с hydrateRoot. Для блога — то же для hero.
- Проверка: LCP-элемент в DevTools Performance/Lighthouse «LCP breakdown»; цель LCP ≤2.5 с на 4G mobile (сейчас запас мал, особенно при росте API-latency).

### 3. [MEDIUM] Hero блога и LCP карточки отдаются в оригинале (jpg/jpeg 1080–1600px, 130–150 КБ), а не в webp-вариантах
- Доказательство: карточка: `uploads/ab3e...jpg` 131 571 байт, натуральные 1600x1600, показывается в 378x283 CSS-px; рядом существует `-w800.webp` (33 626 байт — в 4 раза меньше). Блог: `0b37bfd6...jpeg` 147 397 байт, 1080x721, в 380px. Список/главная при этом корректно используют -w400/-w800 webp.
- Рекомендация: использовать srcset с -w400/-w800 .webp для главного фото карточки и hero статей (при загрузке обложек статей генерировать webp-варианты тем же пайплайном).
- Проверка: размер ответа LCP-картинки в Network (цель ≤40–50 КБ на mobile).

### 4. [MEDIUM] Главная и категории: двойная загрузка картинок и eager для 4–5 карточек
- Доказательство: в списке `<img>` на главной для одних и тех же товаров присутствуют по два элемента (w400 в 96px-превью и w800/w400 в «большом» слайде 412px, `fetchpriority=high`, `loading=eager`); на /arenda-pylesosov-moskva 4 карточки с `eager`+`high` + 4 превью — сразу ~8 картинок конкурируют за канал с H1/CSS/JS. Часть ниже по странице (WD5, Partybox 710, Puzzi 10/1, Okami Q75, DJI Mic 2, Vacmaster) на главной грузится в оригинальном jpg/png (`/uploads/<id>.jpg`, `.png`) вместо webp — то есть не у всех товаров есть -w400.webp (или фронт падает на оригинал при ошибке).
- Рекомендация: eager/high только для 1 первого видимого изображения, остальные lazy; не рендерить дублирующую «большую» картинку для каждой карточки; убедиться, что у всех товаров сгенерированы webp-варианты (иначе `onError`-fallback отдаёт тяжёлые PNG).
- Проверка: Network → Img: сумма байт до `load` на главной, число запросов к /uploads.

### 5. [MEDIUM] Гидратация/JS: долгие задачи и размер бандла
- Доказательство: на главной mobile (4x CPU) сумма «лишнего» времени долгих задач ≈271 мс, на блоге ≈143, на карточке ≈142. DOM главной 1 102 элемента, HTML 160 КБ (gzip ~30 КБ). React+router+query+api vendors ≈ 45+15+10+18 КБ gzip, index.js 39 КБ, плюс 14 modulepreload-чанков (14 доп. запросов к GitHub Pages с max-age=600).
- Рекомендация: отложить не критичные блоки главной (FAQ, отзывы, нижние секции) через `content-visibility: auto`/lazy-компоненты; проверить необходимость api-vendor (axios?) и query-vendor; слить мелкие чанки (api, utils, apiError, analytics…) в 1–2.
- Проверка: Lighthouse TBT, Performance panel (Long Tasks); INP в полевых данных после накопления.

### 6. [MEDIUM] Кэширование статики: max-age=600 на всём, включая хэшированные ассеты
- Доказательство: `cache-control: max-age=600` у `/assets/index.DBlcden-.js`, `/fonts/*.woff2` (x-cache MISS), HTML. Имена ассетов хэшированы, но повторные визиты каждые 10 минут делают условные запросы (ограничение GitHub Pages: нельзя менять заголовки). Картинки на api.vozmimenya.ru, напротив, имеют `public, max-age=31536000, immutable` — хорошо.
- Рекомендация: поставить перед GitHub Pages CDN (Cloudflare/Yandex CDN/Cloud.ru CDN) с правилом `immutable, max-age=31536000` для /assets/* и /fonts/*, HTML — коротко с revalidate; либо отдавать статику с Cloud.ru nginx.
- Проверка: `curl -I https://vozmimenya.ru/assets/<файл>.js | grep -i cache-control`.

### 7. [LOW-MEDIUM] TTFB главной и arenda-* ~0.85–1.0 с (мой канал, одиночный замер), у других страниц 0.3–0.45 с
- Доказательство: navigation.responseStart / | /arenda-pylesosov-moskva = 845–995 мс vs 303–443 мс на блоге/карточке (первое соединение / разный edge Fastly). Порог «хорошо» ≤800 мс. Нужны повторные замеры из нескольких регионов РФ — GitHub Pages (Fastly, ближайший узел FRA) без CDN в РФ.
- Рекомендация: российский CDN/прокси перед Pages; повторно измерить TTFB 5+ раз (WebPageTest/Cloud.ru из Москвы).
- Проверка: `curl -w '%{time_starttransfer}'` 10 раз с серверов в РФ.

### 8. [LOW] Яндекс.Метрика: webvisor + clickmap, грузится после согласия
- Доказательство: `index.html` — загрузка отложена до `load` + 1 с и только при `cookie_consent=accepted` (хорошо для LCP; в лаборатории мы Метрику не видели). `webvisor:true` + `clickmap`+`trackLinks` повышают нагрузку на main thread и риск ухудшения INP у согласившихся пользователей.
- Рекомендация: вебвизор включать выборочно (или отключить), оценить INP в Метрике/CrUX после накопления данных; проверить, что `ym` не подключается заново на SPA-переходах.
- Проверка: Performance panel после принятия cookie, сравнить долгие задачи.

### 9. [LOW] Шрифты: 4 woff2 (~96 КБ), latin-подмножества грузятся на кириллических страницах
- Доказательство: `inter-tight-latin.woff2` 43 КБ и `manrope-latin.woff2` 23 КБ грузятся в начале (цифры, лат. символы в тексте), preload только для cyrillic. `font-display: swap` стоит (FOUT, влияние на CLS не выявлено — CLS=0 на главной/карточке).
- Рекомендация: подгонять метрики fallback (`size-adjust`, `ascent-override`), рассмотреть variable-шрифты/субсет только используемых глифов; убрать лишний вес latin (43 КБ у Inter Tight подозрительно велик — вероятно, variable со всеми осями).
- Проверка: Network → Font; Lighthouse «font-display».

### 10. [LOW] Прочее
- Логотипы PNG (logo-header 13 КБ, logo-footer 15 КБ, max.png 10 КБ, data-URI Avito) — перевести в SVG/webp; `logo-footer` (68x120) отображается как 23x40 — избыточный размер.
- Мёртвый код регистрации SW: в `main.tsx` при каждой загрузке удаляется SW и чистятся CaChe Storage — лишняя работа на load; убрать после того, как у пользователей SW исчезнет.

## Раздел «Изображения» — оценка 74/100

Плюсы (+): у всех `<img>` товаров/статей есть содержательный `alt` («Аренда Karcher Puzzi 8/1», у галереи — «... 1/2/3»); у логотипа в шапке `alt=""` (декоративный, допустимо, но ссылка-логотип должна иметь aria-label); логотипы с width/height; формат webp и адаптивные варианты -w400/-w800 у большинства товаров; нижние картинки lazy; кэш картинок на API `immutable` 1 год.

Минусы (−):
- Контентные картинки без атрибутов width/height (карточки, превью товаров, hero статей: `w=null h=null`) → зависят от CSS и API, риск CLS (см. находки 1–2).
- Для LCP карточки/блога подаётся оригинал JPEG 1080–1600px (130–150 КБ), а webp-варианты есть (≈34 КБ) (находка 3). −10
- На главной/категориях часть товаров грузится в jpg/png-оригиналах, дубли картинок, лишний eager/high (находка 4). −8
- Блог: изображения в тексте оригиналы (750–1080px jpeg/webp) в контейнере 378px; нет srcset. −4
- Значки (Avito как data-URI, Max PNG) не оптимизированы, `logo-footer` передан в 2.8x размере. −2
- Нет preload для LCP-изображений и их нет в пререндер-HTML. −2

Проверка: для списка IMG: размер файла / натуральные / отображаемые, 'Properly size images' и 'Serve images in next-gen formats' в Lighthouse (после правок разница в весе картинок на страницах ≈ −100…−300 КБ).

## Что хорошо
- Один render-blocking CSS ~20 КБ, JS через module (не блокирует), preload кириллических шрифтов, preconnect на API.
- LCP главной и статей на mobile (lab) ≤2.0 с; TBT небольшой; Метрика отложена и за согласием.
- Картинки на API: immutable, HTTP/2, webp-варианты.

## Ограничения
Один прогон на страницу, без Lighthouse и CrUX; INP не измерен; TTFB зависит от моего канала; оценки 66/74 — экспертные, лабораторные.
