# SSR для публичного сайта VozmiMenja

**Дата:** 2026-11-15
**Статус:** дизайн согласован владельцем
**Цель:** перевести публичную часть `vozmimenya.ru` на SSR, сохранив текущую SPA-админку и безопасный откат на статическую сборку.

## Контекст

Сайт работает на Cloud.ru за Nginx. Клиентская часть собрана на React 18, Vite и React Router. Во время production-сборки скрипт `client/scripts/generate-static-route-entrypoints.js` создаёт индексируемый HTML для известных маршрутов, товаров и статей.

Текущая статика уже содержит title, description, canonical, H1, основной текст и JSON-LD. Поэтому SSR внедряется не как единственный способ сделать сайт индексируемым, а чтобы:

- отдавать актуальные данные в первом HTML без обязательной пересборки;
- иметь одну React-реализацию для пользовательского и поискового представления;
- исключить задержку второго этапа JavaScript-рендеринга у поисковых роботов;
- упростить дальнейшее развитие динамических SEO-страниц.

## Объём работ

### Входит

- все публичные страницы основного домена;
- главная, категории, сценарные и локальные посадочные;
- карточки оборудования;
- список и страницы статей;
- информационные и юридические страницы;
- страницы бронирования, включая noindex-страницу успешной заявки;
- серверное формирование метаданных и структурированных данных;
- hydration существующего React-интерфейса;
- отдельный SSR-процесс под PM2;
- Nginx-кеш, статический fallback, мониторинг и поэтапное включение.

### Не входит

- SSR для `/admin/*`;
- изменение API-контрактов, схемы SQLite или бизнес-логики аренды;
- изменение URL-структуры;
- редизайн страниц;
- перенос на Next.js или другой frontend-фреймворк;
- удаление текущего генератора статических страниц в первой поставке;
- production-релиз без отдельной команды владельца «выкатывай».

## Рассмотренные варианты

### 1. Vite SSR поверх текущего React-приложения — выбран

Добавляются серверная и клиентская точки входа, общий маршрутный слой и серверная предзагрузка данных. Существующие компоненты и URL сохраняются. Это минимизирует переписывание и позволяет оставить текущую статику как резерв.

### 2. React Router Framework Mode

Даёт встроенные loaders и SSR-модель, но требует существенно переделать существующий декларативный роутинг и загрузку данных. Возможен позднее как отдельная миграция, если объём серверной логики вырастет.

### 3. Next.js

Потребовал бы переписывания маршрутов, сборки и деплоя. Для текущей задачи стоимость и риск не оправданы.

## Архитектура

### Компоненты

1. `entry-client` подключает React к полученному HTML через `hydrateRoot`.
2. `entry-server` получает URL и подготовленное состояние, рендерит React через `renderToString` и возвращает тело, Helmet-контекст и HTTP-статус.
3. Общий app factory создаёт дерево провайдеров для браузера и сервера: router, React Query, Helmet и остальные глобальные провайдеры.
4. Общий реестр публичных маршрутов определяет компонент, правила предзагрузки, статус и индексируемость. `/admin/*` остаётся в клиентском роутере.
5. SSR HTTP-процесс работает отдельно от API на loopback-порту и имеет собственный `/health`.
6. Nginx отдаёт ассеты и админку напрямую, а публичные HTML-запросы передаёт SSR-процессу.

`renderToString` выбран для первой версии: страницы небольшие, а Nginx-кеш снимает повторную нагрузку. Streaming не входит в первую поставку.

### Поток запроса

1. Клиент запрашивает публичный URL у Nginx.
2. Nginx применяет канонические 301-редиректы и отделяет статические ассеты.
3. SSR-процесс сопоставляет pathname с общим реестром маршрутов.
4. Route loader предзагружает необходимые запросы React Query через локальный API.
5. Сервер формирует React HTML, Helmet head и безопасно сериализованное dehydrated-состояние.
6. Nginx возвращает документ и при необходимости сохраняет его в краткосрочном дисковом кеше.
7. `entry-client` использует те же маршрут и query state для hydration без повторной начальной загрузки.

После hydration клиентские обновления данных продолжают работать через существующий API.

## Данные и единый источник истины

- Query keys и query functions выносятся в общие SSR-safe модули, чтобы сервер и браузер не дублировали правила запросов.
- Для SSR используется loopback API origin; в клиентский bundle попадает только публичный API origin.
- Цены, наличие, оборудование и статьи берутся из production API, а не копируются в SSR-код.
- В dehydrated state разрешены только данные публичных запросов. Токены, переменные окружения и административные данные туда не попадают.
- Сериализация экранирует `<`, `>`, `&`, U+2028 и U+2029, чтобы исключить разрыв script-тега и XSS.
- Дата и случайные значения не должны менять серверную и первую клиентскую разметку.

## Политика маршрутов

- Все существующие публичные canonical URL получают SSR.
- `/admin/*` продолжает обслуживаться как SPA из текущей статической сборки.
- Неизвестный публичный путь возвращает реальный `404` и noindex, а не `200` с экраном ошибки.
- Существующие постоянные редиректы остаются на Nginx и сохраняют query string.
- `/booking/success` рендерится сервером, но остаётся `noindex, nofollow`.
- Один и тот же HTML отдается роботам и пользователям; user-agent branching не используется.

## SEO-контракт

Каждая индексируемая SSR-страница в первом ответе должна содержать:

- уникальный `<title>`;
- meta description;
- canonical на текущий основной URL;
- корректный robots;
- ровно один содержательный H1;
- основной текст и внутренние ссылки;
- релевантный JSON-LD без расхождений с видимым контентом;
- абсолютные индексируемые URL изображений;
- HTTP-статус, соответствующий странице.

SSR не создаёт новые тонкие страницы и не меняет существующую семантику URL.

## Кеширование и устойчивость

- Nginx использует дисковый microcache для безопасных публичных GET/HEAD-запросов.
- Базовый TTL HTML — 60 секунд; ассеты сохраняют текущее длительное кеширование по hash-именам.
- Cache key не разделяется по UTM-параметрам. Персонализированный HTML не допускается.
- `/booking`, `/booking/success`, `/admin/*`, non-GET-запросы и ответы с ошибкой не кешируются.
- При временной ошибке upstream Nginx может отдать последнюю успешную stale-версию.
- При `502`, `503`, `504` или таймауте SSR Nginx переходит к существующему статическому route entrypoint.
- Статический fallback сохраняется минимум две недели после полного переключения.
- API и SSR перезапускаются независимо; сбой SSR не должен останавливать API.

## SSR-совместимость компонентов

До включения маршрута должны быть устранены несовпадения серверного и клиентского рендера:

- `window`, `document`, `navigator`, `localStorage` и `sessionStorage` не читаются во время server render;
- browser-only эффекты выполняются после mount;
- `useLayoutEffect` не используется в компонентах, участвующих в SSR, либо заменяется изоморфным вариантом;
- модальные окна, cookie banner, аналитика и плавающие действия дают детерминированную первую разметку;
- даты, локаль и форматирование явно фиксируются;
- lazy-компоненты имеют одинаковый server/client fallback.

Текущие тесты уже показывают предупреждения `useLayoutEffect` из React Router-компонентов. Они должны быть устранены или доказанно изолированы до production-переключения.

## Ошибки и наблюдаемость

SSR-процесс логирует структурированно:

- route, status, render time и cache-relevant outcome;
- таймауты и ошибки API без персональных данных;
- ошибки рендера с correlation id;
- memory usage и graceful shutdown.

PM2 должен перезапускать SSR при аварии и ограничивать бесконтрольный рост памяти. `/health` проверяет готовность процесса формировать HTML, а не только наличие TCP-порта.

## Проверки

### Автоматические

- unit-тесты route matching и route loaders;
- SSR-контракты для статической, товарной, локальной, блоговой и noindex-страницы;
- наличие title, description, canonical, robots, H1, тела и JSON-LD;
- корректные `200`, `301`, `404`;
- безопасная сериализация dehydrated state;
- отсутствие повторного первоначального API-запроса после hydration;
- Nginx-тесты для SSR proxy, cache bypass, stale и static fallback;
- существующие `test`, `typecheck`, `lint` и production build.

### Браузерные и эксплуатационные

- отсутствие hydration mismatch, runtime-ошибок и ошибок консоли;
- работоспособность навигации, форм, cookie banner и аналитики;
- совпадение цен и контента HTML с API;
- доступность страницы без выполнения JavaScript;
- cold TTFB и cached TTFB на production-подобном окружении;
- контроль памяти SSR/API на VM с 1 ГБ RAM;
- smoke основных URL после каждого этапа переключения.

Целевой cached TTFB — до 500 мс. Для uncached SSR фиксируется baseline до релиза; переключение запрещено при заметном ухудшении относительно текущей статики или при нестабильности под тестовой нагрузкой.

## Выкладка

1. Подготовить SSR build, PM2-конфигурацию и Nginx-конфигурацию без активации proxy.
2. Проверить SSR локально и на VM через loopback-порт.
3. Включить SSR для ограниченного набора маршрутов: информационная страница, одна категория, одна карточка товара и одна статья.
4. Проверить HTML, браузер, логи, память, TTFB и fallback.
5. Расширить SSR на все публичные маршруты, не меняя `/admin/*`.
6. Выполнить production smoke и отправить sitemap на переобход.
7. Наблюдать минимум две недели, сохраняя статическую сборку и быстрый rollback.

Каждое production-переключение требует явного подтверждения владельца «выкатывай».

## Откат

Откат не требует возврата кода или базы:

1. отключить SSR location/upstream в Nginx;
2. вернуть текущую `try_files`-раздачу статических route entrypoints;
3. проверить `nginx -t` и перезагрузить Nginx;
4. выполнить smoke главной, категории, карточки, статьи, локальных страниц и 404.

SSR-процесс после переключения можно остановить отдельно. API, база и статические файлы при откате не изменяются.

## Критерии готовности

- все публичные canonical URL рендерятся на сервере;
- `/admin/*` работает в прежнем SPA-режиме;
- данные первого HTML актуальны и совпадают с API;
- SEO-контракт выполняется для репрезентативных и динамических маршрутов;
- нет hydration mismatch и ошибок браузера;
- реальные `301/404` и static fallback проверены;
- API остаётся доступным при остановленном SSR;
- полный набор тестов, typecheck, lint и build проходит;
- нагрузка укладывается в ресурсы текущей VM;
- документированы rollout, мониторинг и однокомандный rollback;
- production не переключён без отдельного подтверждения владельца.
